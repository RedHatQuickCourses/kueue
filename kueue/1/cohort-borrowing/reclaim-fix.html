Enable Reclaim and Verify

The fix for the reclaim failure is a single configuration change: adding reclaimWithinCohort: Any to the A100 ClusterQueue. The inference deployments from Submit inference Deployments are still running — no need to redeploy.

References

  • Kueue: Preemption (reclaimWithinCohort)

  • Kueue: Cohort

  • Red Hat build of Kueue: Using Cohorts

Lab: Enable and Test Reclaim

1. Enable reclaim — apply reclaimWithinCohort: Any

  1. Review kueue-config/9a-cohort-reclaim-queues.yaml before applying. This file is identical to 9-cohort-cluster-queues.yaml except for one field in the a100-cluster-queue preemption section:

    spec:
  cohortName: gpu-cohort
  preemption:
    withinClusterQueue: LowerPriority
    reclaimWithinCohort: Any                           (1)
    1 reclaimWithinCohort: Any is the only change. This allows the A100 queue to preempt any workload that borrowed its resources via the cohort, regardless of the borrower’s priority. Without this field (the default), the lender cannot reclaim its GPU even when its own workloads need it.

    The t4-cluster-queue is unchanged from the previous cohort configuration.

  2. Apply the configuration:

    $ oc apply -f kueue-config/9a-cohort-reclaim-queues.yaml
clusterqueue.kueue.x-k8s.io/a100-cluster-queue configured
clusterqueue.kueue.x-k8s.io/t4-cluster-queue unchanged

  3. Verify the change:

    $ oc get clusterqueue a100-cluster-queue -o jsonpath='{.spec.preemption.reclaimWithinCohort}'
Any

    You should now see Any. Compare this to the cohort setup config — the only difference is this one field.

The A100 queue shows Total: 4 (all GPUs reclaimed by training).

+ The T4 queue’s a100-gpu flavor shows Borrowed: 0 — the borrowed GPU has been returned.

+

The reclaim sequence:

  1. Jobs 1, 2, and 3 used the 3 available A100 GPUs (4 nominal - 1 lent to inference)

  2. Job 4 needed a GPU but all A100s were occupied (3 training + 1 borrowed by inference)

  3. Kueue identified the borrowing workload on a100-cluster-queue

  4. reclaimWithinCohort: Any authorized preemption of the borrowed workload

  5. The borrowed workload was evicted, freeing 1 A100 GPU for training-reclaim-4

+ IMPORTANT: Contrast with Submit training jobs in the previous section: the same scenario (4 training jobs + 1 borrowed GPU) resulted in job 4 staying Pending indefinitely. The only difference is reclaimWithinCohort: Any in the ClusterQueue spec — one field controls whether a lender can take back its resources.

Which Deployment Gets Evicted?

Kueue does not care about Deployment names — it evicts whichever workload is currently holding the borrowed A100 GPU. In a fresh run (no cluster reboot), that is inference-borrow, because it was the third Deployment to be admitted and the first two (inference-fill-1, inference-fill-2) consumed the T4 quota.

However, if you rebooted the cluster between Submit inference Deployments and this step, the pod placement may have changed. After a reboot, the original pods fail with UnexpectedAdmissionError and the Deployment controller creates replacements. Kueue admits these replacement pods through the normal pipeline, but the order of admission is not guaranteed — any of the three Deployments could end up on the A100 node as the borrower.

For example, you might see inference-fill-1 evicted instead of inference-borrow because after the reboot, fill-1 happened to be the one borrowing from the A100 pool. This is expected behavior. The key takeaway is the same: reclaimWithinCohort: Any allows the lender to reclaim its GPU from any borrower, regardless of which Deployment holds it.

reclaimWithinCohort Options

The reclaimWithinCohort field has three possible values:

  • Never (default) — the lender cannot reclaim resources from borrowers

  • LowerPriority — the lender can reclaim only if the borrowing workload has a lower WorkloadPriorityClass than the pending workload

  • Any — the lender can reclaim from any borrowing workload regardless of priority

In this exercise you use Any for simplicity. In production, LowerPriority is often preferred so that high-priority inference workloads borrowing GPU capacity are not evicted by low-priority training jobs.
