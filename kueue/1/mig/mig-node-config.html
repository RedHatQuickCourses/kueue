Configure MIG on the Node

In this section, you apply MIG labels and the partition annotation to the A100 worker node, then verify that the mig-faker DaemonSet processes the configuration.

Concepts: MIG Node Annotation

The MIG configuration is driven by two pieces of node metadata:

  • Labels — runai-dynamic-mig and runai-mig-enabled tell the fake GPU operator’s mig-faker DaemonSet that this node supports MIG

  • Annotation — run.ai/mig.config defines the MIG partition layout for GPU 0; GPUs 1-3 are not listed and remain as whole devices

Annotation format

The run.ai/mig.config annotation contains a YAML document that tells the mig-faker exactly how to partition each GPU. Here is the annotation used in this lab:

run.ai/mig.config: |
  version: v1
  mig-configs:
    selected:
    - devices: ["0"]          (1)
      mig-enabled: true
      mig-devices:
      - name: 3g.20gb         (2)
        position: 0            (3)
        size: 3                (4)
      - name: 2g.10gb
        position: 4
        size: 2
      - name: 1g.5gb
        position: 6
        size: 1
1 devices — which GPU indices to partition (only GPU 0 in this lab; GPUs 1-3 are not listed and remain as whole devices)
2 name — the MIG profile to create (must match a valid profile for the GPU model, e.g. 3g.20gb on A100 40GB)
3 position — the GPU Instance (GI) slot start position on the compute fabric; this determines where the instance is physically placed on the die
4 size — the number of compute slices consumed (the X in Xg.Ygb)

The mig-devices field must be an array of objects, not a map. Positions must not overlap — each MIG instance occupies size consecutive compute slots starting at position.

Lab: Apply MIG Node Configuration

1. Edit the MIG node configuration

The MIG labels and partition annotation are defined in a single YAML file. Before applying, you must replace the placeholder node name with $WORKER_NODE1 (set in Setting Worker Node Variables).

Verify the variable is set:

$ echo $WORKER_NODE1

Edit the file and replace the placeholder node name with the value of $WORKER_NODE1:

$ vi kueue-config/6a-mig-node-config.yaml

You can also use sed to do the replacement automatically:

$ sed -i "s/worker-cluster-fn765-1/$WORKER_NODE1/" kueue-config/6a-mig-node-config.yaml

2. Apply the MIG node configuration

Review kueue-config/6a-mig-node-config.yaml before applying:

apiVersion: v1
kind: Node
metadata:
  name: worker-cluster-fn765-1              (1)
  labels:
    node-role.kubernetes.io/runai-dynamic-mig: "true"  (2)
    node-role.kubernetes.io/runai-mig-enabled: "true"   (2)
  annotations:
    run.ai/mig.config: |                    (3)
      version: v1
      mig-configs:
        selected:
        - devices: ["0"]                    (4)
          mig-enabled: true
          mig-devices:
          - name: 3g.20gb                   (5)
            position: 0
            size: 3
          - name: 2g.10gb
            position: 4
            size: 2
          - name: 1g.5gb
            position: 6
            size: 1
1 Must match your actual A100 node name (replaced in step 1).
2 These labels tell the mig-faker DaemonSet that this node supports MIG partitioning.
3 The run.ai/mig.config annotation defines the entire MIG partition layout as an inline YAML document.
4 devices: ["0"] partitions only GPU 0. GPUs 1-3 are not listed and remain as whole devices.
5 Each mig-devices entry specifies a MIG profile: name is the profile, position is the starting compute slice index, and size is the number of compute slices consumed. 
$ oc apply -f kueue-config/6a-mig-node-config.yaml
node/worker-cluster-vnnbf-1 configured

This applies both the MIG labels and the partition annotation to the node in a single step.

Never run oc delete -f kueue-config/6a-mig-node-config.yaml — this would delete the entire Node object from the cluster, not just the labels and annotations. To remove MIG configuration, use the individual oc annotate and oc label removal commands in Undo MIG.

Verify the labels and annotation:

Check the MIG labels:

$ oc get node $WORKER_NODE1 --show-labels | tr ',' '\n' | grep -E 'mig|dynamic'
worker-cluster-vnnbf-1   Ready    runai-dynamic-mig
runai-mig-enabled
node-role.kubernetes.io/runai-dynamic-mig=true
node-role.kubernetes.io/runai-mig-enabled=true
nvidia.com/mig.config.state=success
nvidia.com/mig.strategy=mixed

Check the annotation:

$ oc get node $WORKER_NODE1 -o jsonpath='{.metadata.annotations.run\.ai/mig\.config}'
version: v1
mig-configs:
  selected:
  - devices: ["0"]
    mig-enabled: true
    mig-devices:
    - name: 3g.20gb
      position: 0
      size: 3
    - name: 2g.10gb
      position: 4
      size: 2
    - name: 1g.5gb
      position: 6
      size: 1

You should see both labels set to true and the MIG config annotation with three mig-devices entries.

Understanding the Annotation

The mig-devices section uses GPU Instance (GI) slot positions — these are starting compute slice indices that define where each MIG instance is physically placed on the GPU die.

Position Profile Compute Slices Memory

0

3g.20gb

Slices 0-2 (3 of 7)

20 GiB (4 of 8 partitions)

4

2g.10gb

Slices 4-5 (2 of 7)

10 GiB (2 of 8 partitions)

6

1g.5gb

Slice 6 (1 of 7)

5 GiB (1 of 8 partitions)

This uses 6 of 7 compute slices and 7 of 8 memory partitions (35 GiB of 40 GiB). Compute slice 3 is a gap — the A100 MIG architecture requires specific alignment for each profile size.

3. Verify the mig-faker processed the annotation

The mig-faker DaemonSet watches for the run.ai/mig.config annotation. When it sees it, it validates the MIG layout, generates device UUIDs, and sets a success label on the node.

Wait about 15 seconds, then check:

$ oc get node $WORKER_NODE1 -o jsonpath='{.metadata.labels.nvidia\.com/mig\.config\.state}'
success

Expected output: success

If the label is blank or missing, see Troubleshooting MIG.
