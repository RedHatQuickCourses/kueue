Training Jobs — FIFO Admission

In this exercise, you submit three training Jobs with no WorkloadPriorityClass. Without priority, Kueue admits workloads in submission order — first-in, first-out (FIFO).

Concepts

When no WorkloadPriorityClass is set on a workload, Kueue uses FIFO ordering within the ClusterQueue. The first workload to arrive is the first to be admitted, as long as there is sufficient quota.

In this exercise, each Job requests 1 GPU. With 4 A100 GPUs available and only 3 GPUs requested in total, all three Jobs are admitted immediately — there is no contention.

Lab: Submit FIFO Training Jobs

1. Submit training jobs (FIFO — no priority)

  1. Review workloads/job-no-priority.yaml before applying. Only the first Job is shown here — the other two (training-job-medium, training-job-high) follow the same structure:

    apiVersion: batch/v1
kind: Job
metadata:
  name: training-job-low
  namespace: training-jobs                        (1)
  labels:
    kueue.x-k8s.io/queue-name: training-queue     (2)
spec:
  suspend: true                                   (3)
  template:
    metadata:
      annotations:
        run.ai/simulated-gpu-utilization: "40-60"  (4)
    spec:
      restartPolicy: Never
      containers:
      - name: training-workload
        image: registry.access.redhat.com/ubi9/ubi
        command: ["/bin/bash", "-c"]
        args:
        - |
          echo "=== Job: training-job-low (no priority) ==="
          ...
          nvidia-smi                               (5)
          sleep 5
          ...
        resources:
          requests:
            cpu: "2"
            memory: "4Gi"
            nvidia.com/gpu: "1"                    (6)
          limits:
            nvidia.com/gpu: "1"
    1 All three Jobs are created in the training-jobs namespace, which is labeled kueue.openshift.io/managed: "true".
    2 The queue-name label routes the Job to the training-queue LocalQueue, which forwards it to a100-cluster-queue.
    3 suspend: true is required for Kueue-managed Jobs. Kueue holds the Job in a suspended state until it is admitted, then sets suspend: false to start it.
    4 The run.ai/simulated-gpu-utilization annotation tells the Fake GPU Operator what GPU utilization percentage to report in nvidia-smi output.
    5 Each Job runs nvidia-smi every 5 seconds for 5 minutes. The output shows the GPU model name, confirming the pod landed on the correct node.
    6 Each Job requests 1 GPU. With 3 Jobs requesting 1 GPU each and 4 A100 GPUs available, all three are admitted immediately — no contention.

    None of the Jobs carry a kueue.x-k8s.io/priority-class label, so Kueue admits them in FIFO order.

  2. Apply the workloads:

    $ oc apply -f workloads/job-no-priority.yaml
job.batch/training-job-low created
job.batch/training-job-medium created
job.batch/training-job-high created

    This creates three Jobs in the training-jobs namespace:

    Job GPUs Priority Expected Behavior

    training-job-low

    1

    None (FIFO)

    Admitted — order depends on submission

    training-job-medium

    1

    None (FIFO)

    Admitted — order depends on submission

    training-job-high

    1

    None (FIFO)

    Admitted — order depends on submission

    With 3 GPUs requested and 4 available on the A100 node, all three Jobs are admitted immediately.

    $ oc delete jobs -n training-jobs training-job-low training-job-medium training-job-high
job.batch "training-job-low" deleted from training-jobs namespace

    Always clean up workloads before starting the next exercise. Left-over Jobs consume GPU quota and may cause the next exercise’s workloads to remain pending.
