Apply RBAC Bindings

In this section, you create the ClusterRoleBindings and RoleBindings that assign the Kueue roles to your users.

References

  • Kubernetes: RoleBinding and ClusterRoleBinding

  • OpenShift: Using RBAC

  • Red Hat build of Kueue: Configuring Role-Based Permissions

Lab: Create RBAC Bindings

1. Apply batch admin bindings

The admin bindings file contains two resources: a ClusterRoleBinding for cluster-wide Kueue access, and a RoleBinding for pod/log access in the training-jobs namespace.

  1. Review kueue-config/11-rbac-batch-admin.yaml before applying:

    apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding                              (1)
metadata:
  name: kueue-batch-admin-binding
subjects:
- kind: User
  name: admin                                         (2)
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: kueue-batch-admin-role                        (3)
  apiGroup: rbac.authorization.k8s.io
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding                                     (4)
metadata:
  name: admin-edit
  namespace: training-jobs
subjects:
- kind: User
  name: admin
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: edit                                          (5)
  apiGroup: rbac.authorization.k8s.io
    1 ClusterRoleBinding — cluster-wide scope because ClusterQueues, ResourceFlavors, and WorkloadPriorityClasses are cluster-scoped resources.
    2 Replace admin with the actual admin username on your cluster.
    3 kueue-batch-admin-role — the aggregated ClusterRole deployed by the Kueue operator. Grants full CRUD on all Kueue resources and Jobs.
    4 A separate RoleBinding in the training-jobs namespace for pod/log access.
    5 The OpenShift edit ClusterRole fills the gap — Kueue roles don’t cover pods, logs, events, or configmaps.

  2. Apply the admin bindings:

    $ oc apply -f kueue-config/11-rbac-batch-admin.yaml
clusterrolebinding.rbac.authorization.k8s.io/kueue-batch-admin-binding created
rolebinding.rbac.authorization.k8s.io/admin-edit created

2. Apply batch user bindings

The user bindings file contains two RoleBindings, both scoped to the training-jobs namespace.

Why RoleBinding and not ClusterRoleBinding for batch users?

This is a deliberate design choice with an important trade-off.

A ClusterRoleBinding grants the ClusterRole’s permissions cluster-wide. A RoleBinding grants them only in the specified namespace.

Using a RoleBinding means:

  • Intended: The user can only see LocalQueues, Workloads, and pods in training-jobs — not in other teams' namespaces.

  • Side effect: ClusterQueues are cluster-scoped resources. A RoleBinding cannot grant access to cluster-scoped resources, so the user’s get, list, watch permission on ClusterQueues silently has no effect. The user will see Forbidden when trying oc get clusterqueues.

The Kueue project chose namespace isolation over ClusterQueue visibility. If your users need to see ClusterQueues, you would create a separate ClusterRoleBinding referencing kueue-clusterqueue-viewer-role for that user — but be aware this grants cluster-wide visibility.

  1. Review kueue-config/12-rbac-batch-user.yaml before applying. Here is the first RoleBinding:

    apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding                                     (1)
metadata:
  name: kueue-batch-user-binding
  namespace: training-jobs                             (2)
subjects:
- kind: User
  name: user1                                         (3)
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: kueue-batch-user-role                         (4)
  apiGroup: rbac.authorization.k8s.io
    1 RoleBinding (not ClusterRoleBinding) — the batch user’s access is namespace-scoped, unlike the admin’s cluster-wide binding.
    2 Scoped to training-jobs only. The user cannot see queues or workloads in other namespaces.
    3 Replace user1 with the actual batch user’s username on your cluster.
    4 kueue-batch-user-role — grants full CRUD on Jobs, plus read-only access (get, list, watch) to LocalQueues, Workloads, and ClusterQueues. Because this is a RoleBinding (not a ClusterRoleBinding), the cluster-scoped ClusterQueue permission does not take effect.

    The file also contains a second RoleBinding (user1-edit) that grants the edit ClusterRole in training-jobs — the same pattern as the admin bindings above, giving the user access to pods, logs, and events.

  2. Apply the user bindings:

    $ oc apply -f kueue-config/12-rbac-batch-user.yaml
rolebinding.rbac.authorization.k8s.io/kueue-batch-user-binding created
rolebinding.rbac.authorization.k8s.io/user1-edit created

3. Verify all bindings

  1. Check the cluster-wide binding:

    $ oc get clusterrolebinding kueue-batch-admin-binding
NAME                        ROLE                                 AGE
kueue-batch-admin-binding   ClusterRole/kueue-batch-admin-role   71s

  2. Check the namespace-scoped bindings:

    $ oc get rolebindings -n training-jobs
