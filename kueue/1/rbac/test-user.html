Test Batch User Permissions

Log in as the batch user user1 and verify the restricted access — full Job management but limited access to Kueue infrastructure.

The results in this section may surprise you. Some permissions come from the Kueue role you bound, some from RHOAI defaults, and some from the OpenShift edit role. Pay attention to the source of each permission — understanding which layer grants which access is the key takeaway of this exercise.

References

  • Kueue: RBAC

  • Kubernetes: RBAC Authorization

  • Red Hat build of Kueue: Configuring Role-Based Permissions

Lab: Verify User Access and Restrictions

1. Log in as the batch user

RHDP users can find the password for user1 in the My Services page of RHDP. Click on the Users tab to see the password for user1. 
$ oc login -u user1 -p <password> <cluster API url>
Login successful

$ oc whoami
user1

2. Submit a job (should succeed)

The primary purpose of the batch user role is to let users submit Jobs to Kueue-managed queues. This is the same test Job used in Test Admin.

$ oc apply -f workloads/job-rbac-test.yaml
job.batch/rbac-test-job created

The user can create Jobs in the training-jobs namespace because kueue-batch-user-role includes full CRUD on batch/v1 Jobs.

This is the primary use case for the batch user role — data scientists submit training jobs without needing admin access to the cluster’s queue configuration.

  1. View available queues in the namespace:

4. View cluster-scoped Kueue resources (mixed results)

This test demonstrates the most common source of confusion in Kueue RBAC.

The kueue-batch-user-role includes get, list, watch on ClusterQueues. You might expect the user to be able to view them. But the role is bound via a RoleBinding (namespace-scoped), and ClusterQueues are cluster-scoped resources. A RoleBinding cannot grant cluster-scoped permissions — only a ClusterRoleBinding can.

  1. View ClusterQueues — this fails because a RoleBinding cannot grant cluster-scope access:

    $ oc get clusterqueues
Error from server (Forbidden): clusterqueues.kueue.x-k8s.io is forbidden:
User "user1" cannot list resource "clusterqueues" in API group "kueue.x-k8s.io"
at the cluster scope
    Why does the role include ClusterQueue permissions if they don’t work?

    The kueue-batch-user-role is designed to work with either a RoleBinding or a ClusterRoleBinding. If bound with a ClusterRoleBinding, the user would be able to view ClusterQueues cluster-wide. The Kueue project includes ClusterQueue permissions in the user role to support both binding types — the binding is what controls the effective scope, not the role itself.

    In this lab, you use a RoleBinding because namespace isolation is the higher priority.

  2. View ResourceFlavors — this succeeds due to RHOAI default cluster permissions:

    $ oc get resourceflavors
NAME                AGE
a100-gpu            28h
default-flavor      32h
nvidia-gpu-flavor   32h
t4-gpu              28h

  3. View WorkloadPriorityClasses — this also succeeds via RHOAI defaults:

    $ oc get workloadpriorityclasses
NAME              VALUE
high-priority     1000
low-priority      100
medium-priority   500
    ResourceFlavors and WorkloadPriorityClasses are accessible to all authenticated users on RHOAI clusters through default permissions set by the operator. This access does not come from kueue-batch-user-role or any binding you created. Even a user with zero Kueue bindings would see the same output.

5. Modify Kueue infrastructure (should fail)

The batch user can view some Kueue resources but cannot create, modify, or delete them.

  1. Try to delete a LocalQueue:

    $ oc delete localqueue training-queue -n training-jobs
Error from server (Forbidden): localqueues.kueue.x-k8s.io "training-queue"
is forbidden: User "user1" cannot delete resource "localqueues"
in API group "kueue.x-k8s.io" in the namespace "training-jobs"

  2. Try to create a ClusterQueue:

    $ oc auth can-i create clusterqueues.kueue.x-k8s.io
Warning: resource 'clusterqueues' is not namespace scoped in group 'kueue.x-k8s.io'
no

  3. Try to create a LocalQueue:

    $ oc auth can-i create localqueues.kueue.x-k8s.io -n training-jobs
no

    The batch user has read-only access to namespace-scoped Kueue resources (LocalQueues, Workloads) but cannot create, modify, or delete ClusterQueues or LocalQueues.

    On RHOAI clusters, default permissions allow all authenticated users to create and delete ResourceFlavors and WorkloadPriorityClasses. This is not something the kueue-batch-user-role grants — it comes from RHOAI operator defaults. In production, restrict these permissions with additional RBAC policies.

6. Access other namespaces (should fail)

  1. Try to view LocalQueues in inference-apps (no RoleBinding there):

    $ oc get localqueues -n inference-apps
Error from server (Forbidden): localqueues.kueue.x-k8s.io is forbidden:
User "user1" cannot list resource "localqueues" in API group "kueue.x-k8s.io"
in the namespace "inference-apps"

  2. Try to view pods in inference-apps:

    $ oc get pods -n inference-apps
Error from server (Forbidden): pods is forbidden:
User "user1" cannot list resource "pods" in API group ""
in the namespace "inference-apps"

    Both fail — the batch user’s RoleBinding is scoped to training-jobs only. To give user1 access to another namespace (e.g., inference-apps), you would create additional RoleBindings in that namespace.

7. Clean up

$ oc delete job rbac-test-job -n training-jobs
job.batch "rbac-test-job" deleted
