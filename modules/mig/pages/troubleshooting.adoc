= Troubleshooting MIG
:navtitle: Troubleshooting

If xref:verify-mig.adoc#check-mig-resources[Check MIG resources] still shows `nvidia.com/gpu: 4` with no MIG resources, work through these checks in order.

== 1. Is the mig-faker Pod Running?

[source,console,subs="+quotes"]
----
$ **oc get daemonset mig-faker -n gpu-operator**
----

If `DESIRED` is `0`, the mig-faker cannot schedule on your node.
The most common cause is a *missing toleration* -- the GPU node has a `nvidia.com/gpu=present:NoSchedule` taint, but the mig-faker DaemonSet may not tolerate it.
Fix with:

[source,console,subs="+quotes"]
----
$ **oc patch daemonset mig-faker -n gpu-operator --type=json** \
  **-p '[{"op":"add","path":"/spec/template/spec/tolerations","value":[{"key":"nvidia.com/gpu","operator":"Exists","effect":"NoSchedule"}]}]'**
----

After patching, verify the pod starts:

[source,console,subs="+quotes"]
----
$ **oc get daemonset mig-faker -n gpu-operator**
----

`DESIRED` and `READY` should both be `1`.

== 2. Did the mig-faker Process the Annotation?

[source,console,subs="+quotes"]
----
$ **oc logs -n gpu-operator -l app=mig-faker --tail=20**
----

* *Success:* Look for `Successfuly updated MIG config` and `Labelling node ... mig.config.state:success`
* *Parse error:* If you see `failed to unmarshal mig config`, the annotation format is wrong.
The `mig-devices` field must be an array of objects (`- name: ... position: ... size: ...`), not a map (`0: 3g.20gb`).
See xref:mig-node-config.adoc#edit-mig-config[Edit the MIG node configuration] for the correct format.

== 3. Did You Update the Topology ConfigMap?

[source,console,subs="+quotes"]
----
$ **oc get configmap topology-$WORKER_NODE1 -n gpu-operator -o yaml | grep -A 5 otherDevices**
----

If `otherDevices` is missing, you skipped xref:topology-update.adoc#update-topology[Update the topology ConfigMap].
The device-plugin only knows about resources listed in this ConfigMap.

== 4. Did You Restart the Device-Plugin?

The device-plugin reads the ConfigMap once at startup.
If you updated the ConfigMap but didn't restart the pod (xref:topology-update.adoc#restart-device-plugin[Restart the device-plugin pod]), the device-plugin is still serving the old inventory.
Check the device-plugin logs:

[source,console,subs="+quotes"]
----
$ **oc logs -n gpu-operator $(oc get pods -n gpu-operator -l app=device-plugin** \
  **-o jsonpath="{.items[?(@.spec.nodeName==\"$WORKER_NODE1\")].metadata.name}") --tail=10**
----

You should see lines like `Starting device plugin for RealNodeDevicePlugin-nvidia.com/mig-3g.20gb`.
If you only see `RealNodeDevicePlugin-nvidia.com/gpu`, the pod is using the old ConfigMap -- restart it per xref:topology-update.adoc#restart-device-plugin[Restart the device-plugin pod].

== 5. MIG Processing Pipeline Summary

[cols="1,2,3,3", options="header"]
|===
|Stage |Component |What it does |How to verify

|1
|`6a-mig-node-config.yaml`
|Sets MIG labels + annotation on node
|`oc get node ... -o jsonpath='{.metadata.annotations.run\.ai/mig\.config}'`

|2
|mig-faker DaemonSet
|Validates annotation, sets success label
|`oc get node ... -o jsonpath='{.metadata.labels.nvidia\.com/mig\.config\.state}'` -> `success`

|3
|`6b-mig-topology-update.yaml`
|Updates topology ConfigMap with MIG resources
|`oc get cm topology-$WORKER_NODE1 -n gpu-operator -o yaml \| grep otherDevices`

|4
|device-plugin restart
|Re-reads ConfigMap, advertises MIG to kubelet
|`oc get node ... -o jsonpath='{.status.allocatable}' \| python3 -m json.tool \| grep mig`
|===
