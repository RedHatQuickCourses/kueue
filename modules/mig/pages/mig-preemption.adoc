= MIG Priority Preemption
:navtitle: MIG Preemption

In the previous section, the MIG workloads all fit simultaneously -- one job per profile, no contention.
But what happens when two jobs compete for the same MIG slice?
The `mig-cluster-queue` has `withinClusterQueue: LowerPriority` preemption, which means a high-priority job can evict a low-priority one occupying the same MIG resource.

In this exercise, low-priority jobs fill all three MIG slots.
Then a high-priority job arrives requesting the largest slice (`3g.20gb`).
Kueue preempts the low-priority job on that slice and admits the high-priority one in its place.

== Prerequisites

This exercise requires the MIG configuration from the previous sections.
Ensure:

* Worker-1 has MIG labels and annotations applied
* `mig-cluster-queue`, `a100-mig` flavor, and `mig-training-queue` exist
* WorkloadPriorityClasses (`low-priority`, `high-priority`) exist from xref:kueue-config:priority-classes.adoc[Create WorkloadPriorityClasses^]

Clean up any workloads from previous exercises:

[source,console,subs="+quotes"]
----
$ **oc delete jobs --all -n training-jobs 2>/dev/null**
----

== Lab: MIG Priority Preemption Exercise

=== 1. Fill all MIG slots with low-priority jobs

Submit three low-priority jobs, one per MIG profile.
This saturates all MIG capacity on GPU 0.

Review `workloads/job-mig-fill-low.yaml` before applying.
The file contains three Jobs; here is one representative Job:

[source,yaml]
----
apiVersion: batch/v1
kind: Job
metadata:
  name: mig-fill-3g-20gb                              # <1>
  namespace: training-jobs
  labels:
    kueue.x-k8s.io/queue-name: mig-training-queue
    kueue.x-k8s.io/priority-class: low-priority       # <2>
spec:
  suspend: true
  template:
    metadata:
      annotations:
        run.ai/simulated-gpu-utilization: "70-90"
    spec:
      restartPolicy: Never
      containers:
      - name: mig-workload
        image: registry.access.redhat.com/ubi9/ubi
        command: ["/bin/bash", "-c"]
        args: [...]
        resources:
          requests:
            cpu: "2"
            memory: "8Gi"
            nvidia.com/mig-3g.20gb: "1"                # <3>
          limits:
            nvidia.com/mig-3g.20gb: "1"
----
<1> Each fill job is named after the MIG profile it occupies.
<2> `low-priority` (value 100) -- these jobs will be preempted when a higher-priority job arrives requesting the same MIG profile.
<3> Requests the `3g.20gb` MIG slice. The other two Jobs in the file request `mig-2g.10gb` and `mig-1g.5gb` respectively.

[source,console,subs="+quotes"]
----

----

=== 2. Submit a high-priority job to trigger preemption

Now submit a high-priority job that requests the same `3g.20gb` MIG slice.
Since the slot is occupied by a low-priority job and the ClusterQueue has `withinClusterQueue: LowerPriority`, Kueue preempts the low-priority job.

Review `workloads/job-mig-preempt-high.yaml` before applying:

[source,yaml]
----
apiVersion: batch/v1
kind: Job
metadata:
  name: mig-preempt-high-3g                           # <1>
  namespace: training-jobs
  labels:
    kueue.x-k8s.io/queue-name: mig-training-queue
    kueue.x-k8s.io/priority-class: high-priority      # <2>
spec:
  suspend: true
  template:
    metadata:
      annotations:
        run.ai/simulated-gpu-utilization: "80-95"
    spec:
      restartPolicy: Never
      containers:
      - name: mig-workload
        image: registry.access.redhat.com/ubi9/ubi
        command: ["/bin/bash", "-c"]
        args: [...]
        resources:
          requests:
            cpu: "2"
            memory: "8Gi"
            nvidia.com/mig-3g.20gb: "1"                # <3>
          limits:
            nvidia.com/mig-3g.20gb: "1"
----
<1> The job name indicates it is a high-priority preemption job targeting the `3g` profile.
<2> `high-priority` (value 1000) -- 10x higher than the `low-priority` jobs filling the slots. This triggers Kueue's `LowerPriority` preemption.
<3> Requests the same `mig-3g.20gb` resource as `mig-fill-3g-20gb`. Since quota is 1 and the slot is occupied by a lower-priority job, Kueue preempts it.

[source,console,subs="+quotes"]
----
$ **oc apply -f workloads/job-mig-preempt-high.yaml**
job.batch/mig-preempt-high-3g created
----

This creates:

[cols="2,2,1,1,2", options="header"]
|===
|Job |MIG Resource |Priority |Value |Expected Behavior

|`mig-preempt-high-3g`
|`nvidia.com/mig-3g.20gb: 1`
|`high-priority`
|1000
|*Preempts* `mig-fill-3g-20gb`
|===

.MIG Preemption in Production
[sidebar]
****
In a production cluster with multiple MIG-partitioned GPUs, the preemption behavior scales naturally.
Each MIG profile is a separate Kubernetes extended resource, so Kueue tracks contention per-profile independently.
A high-priority job requesting `mig-3g.20gb` only preempts other jobs using `mig-3g.20gb` -- jobs on smaller profiles are unaffected.
This makes MIG especially useful for mixed workloads where different teams need different GPU sizes.
****
