= Demonstrate Cohort Borrowing
:navtitle: Borrowing

In this section, you fill the T4 inference pool and submit a third workload that borrows from the A100 training pool.
The borrowed pod lands on the A100 node -- you can see this in the `nvidia-smi` output.

== References

* https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/#cohort[Kueue: Cohort^]
* https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/#flavors-and-resources[Kueue: Flavors and Resources^]
* https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html-single/ai_workloads/index#using-cohorts[Red Hat build of Kueue: Using Cohorts^]

== Lab: Trigger and Verify Borrowing

[[submit-borrowing]]
=== 1. Submit inference Deployments to trigger borrowing

a. Review `workloads/deployment-cohort-borrowing.yaml` before applying.
The file contains three Deployments that all submit to `inference-queue`.
Only the borrowing Deployment is shown here -- `inference-fill-1` and `inference-fill-2` follow the same structure:
+

[source,yaml]
----
apiVersion: apps/v1
kind: Deployment
metadata:
  name: inference-borrow                               <1>
  namespace: inference-apps
  labels:
    kueue.x-k8s.io/queue-name: inference-queue         <2>
spec:
  replicas: 1
  selector:
    matchLabels:
      app: inference-borrow
  template:
    ...
    spec:
      containers:
      - name: inference-workload
        image: registry.access.redhat.com/ubi9/ubi
        ...
        resources:
          requests:
            nvidia.com/gpu: "1"                        <3>
----
<1> Three Deployments are defined: `inference-fill-1`, `inference-fill-2` (fill the T4 pool), and `inference-borrow` (triggers borrowing).
<2> All three submit to `inference-queue`, which routes to `t4-cluster-queue`. Kueue tries the `t4-gpu` flavor first.
<3> Each requests 1 GPU. With only 2 T4 GPUs available, the third Deployment exhausts the T4 flavor and Kueue falls back to the `a100-gpu` flavor -- borrowing 1 GPU from the cohort.

b. Apply the workloads:
+
[source,console,subs="+quotes"]
----
$ **oc apply -f workloads/deployment-cohort-borrowing.yaml**
deployment.apps/inference-fill-1 created
deployment.apps/inference-fill-2 created
deployment.apps/inference-borrow created
----
+
This creates:

[cols="2,1,3,2", options="header"]
|===
|Deployment |GPUs |Purpose |Expected Node

|`inference-fill-1`
|1
|Fills T4 slot 1 of 2
|worker-2 (T4)

|`inference-fill-2`
|1
|Fills T4 slot 2 of 2
|worker-2 (T4)

|`inference-borrow`
|1
|Borrows from A100 pool
|worker-1 (A100)
|===

All three submit to `inference-queue` -> `t4-cluster-queue`.
Kueue admits the first two using the `t4-gpu` flavor.
For the third, the T4 flavor's quota is exhausted, so Kueue tries the fallback `a100-gpu` flavor and borrows 1 GPU from the cohort.

TIP: The GPU product name difference is the proof: the borrowed pod sees an A100, not a T4, even though it submitted to the same inference queue as the others.
This confirms that flavor fungibility is working -- Kueue fell back from `t4-gpu` to `a100-gpu`.

c. Check ClusterQueue borrowing status:
+
[source,console,subs="+quotes"]
----
$ **oc describe clusterqueue t4-cluster-queue | grep -A 25 "Flavors Usage" | grep -B 1 -A 1 "nvidia.com/gpu"**
      Borrowed:  0
      Name:      nvidia.com/gpu
      Total:     2
--
      **Borrowed:         1**
      Name:             nvidia.com/gpu
      Total:            1
----

The first block is the `t4-gpu` flavor (own quota: 2 GPUs, Borrowed: 0).
The second block is the `a100-gpu` flavor -- *Borrowed: 1* confirms the third Deployment is using a GPU borrowed from the A100 pool.

NOTE: Lending is tracked on the *borrower's* side, not the lender's.
The `t4-cluster-queue` shows `Borrowed: 1` under its `a100-gpu` flavor.
The `a100-cluster-queue` does *not* show a "lent out" counter -- Kueue tracks borrowing from the borrower's perspective.
To see that the A100 pool has capacity tied up, check that `inference-borrow` pod is running on the A100 node (`oc get pods -n inference-apps -o wide`).
