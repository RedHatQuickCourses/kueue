= Enable Reclaim and Verify
:navtitle: Reclaim Fix

The fix for the reclaim failure is a single configuration change: adding `reclaimWithinCohort: Any` to the A100 ClusterQueue.
The inference deployments from xref:borrowing.adoc#submit-borrowing[Submit inference Deployments] are still running -- no need to redeploy.

== Lab: Enable and Test Reclaim

=== 1. Enable reclaim -- apply `reclaimWithinCohort: Any`

a. Review `kueue-config/9a-cohort-reclaim-queues.yaml` before applying.
This file is identical to `9-cohort-cluster-queues.yaml` except for one field in the `a100-cluster-queue` preemption section:
+

[source,yaml]
----
spec:
  cohortName: gpu-cohort
  preemption:
    withinClusterQueue: LowerPriority
    reclaimWithinCohort: Any                           <1>
----
<1> `reclaimWithinCohort: Any` is the only change. This allows the A100 queue to preempt *any* workload that borrowed its resources via the cohort, regardless of the borrower's priority. Without this field (the default), the lender cannot reclaim its GPU even when its own workloads need it.
+
The `t4-cluster-queue` is unchanged from the previous cohort configuration.

b. Apply the configuration:
+
[source,console,subs="+quotes"]
----
$ **oc apply -f kueue-config/9a-cohort-reclaim-queues.yaml**
clusterqueue.kueue.x-k8s.io/a100-cluster-queue configured
clusterqueue.kueue.x-k8s.io/t4-cluster-queue unchanged
----

c. Verify the change:
+
[source,console,subs="+quotes"]
----
$ **oc get clusterqueue a100-cluster-queue -o jsonpath='{.spec.preemption.reclaimWithinCohort}'**
Any
----
+
You should now see `Any`.
Compare this to the xref:cohort-setup.adoc#apply-cohort[cohort setup] config -- the only difference is this one field.

b. Confirm the borrowed workload was evicted:
+
[source,console,subs="+quotes"]
----
$ **oc get pods -n inference-apps -o wide**
NAME                                READY   STATUS            RESTARTS   AGE   IP            NODE                     NOMINATED NODE   READINESS GATES
inference-borrow-75f897fcb8-p5h2n   1/1     Running           0          33m   10.232.2.12   worker-cluster-vnnbf-2   <none>           <none>

----
+
One of the inference Deployments that was borrowing an A100 GPU has been evicted.
The Deployment controller created a replacement pod, but Kueue holds it in `SchedulingGated` status because there is no GPU available to borrow -- all 4 A100 GPUs are now occupied by training jobs, and the T4 pool is full.
See the sidebar at the bottom of this page for details on which Deployment gets evicted and why.

c. Check ClusterQueue status:
+
[source,console,subs="+quotes"]
----
$ **oc describe clusterqueue a100-cluster-queue | grep -A 25 "Flavors Usage" | grep -B 1 -A 1 "nvidia.com/gpu"**
      Borrowed:  0
      Name:      nvidia.com/gpu
      **Total:     4**

$ **oc describe clusterqueue t4-cluster-queue | grep -A 25 "Flavors Usage" | grep -B 1 -A 1 "nvidia.com/gpu"**
      Borrowed:  0
      Name:      nvidia.com/gpu
      Total:     2
--
      **Borrowed:         0**
      Name:             nvidia.com/gpu
      Total:            0
----

The A100 queue shows Total: 4 (all GPUs reclaimed by training).
+
The T4 queue's `a100-gpu` flavor shows Borrowed: 0 -- the borrowed GPU has been returned.
+
[TIP]
====
*The reclaim sequence:*

. Jobs 1, 2, and 3 used the 3 available A100 GPUs (4 nominal - 1 lent to inference)
. Job 4 needed a GPU but all A100s were occupied (3 training + 1 borrowed by inference)
. Kueue identified the borrowing workload on `a100-cluster-queue`
. `reclaimWithinCohort: Any` authorized preemption of the borrowed workload
. The borrowed workload was evicted, freeing 1 A100 GPU for `training-reclaim-4`
====
+
IMPORTANT: Contrast with xref:reclaim-failure.adoc#submit-nopreempt[Submit training jobs] in the previous section: the same scenario (4 training jobs + 1 borrowed GPU) resulted in job 4 staying *Pending* indefinitely.
The only difference is `reclaimWithinCohort: Any` in the ClusterQueue spec -- one field controls whether a lender can take back its resources.

.Which Deployment Gets Evicted?
[sidebar]
****
Kueue does not care about Deployment names -- it evicts whichever workload is *currently holding the borrowed A100 GPU*.
In a fresh run (no cluster reboot), that is `inference-borrow`, because it was the third Deployment to be admitted and the first two (`inference-fill-1`, `inference-fill-2`) consumed the T4 quota.

However, if you rebooted the cluster between xref:borrowing.adoc#submit-borrowing[Submit inference Deployments] and this step, the pod placement may have changed.
After a reboot, the original pods fail with `UnexpectedAdmissionError` and the Deployment controller creates replacements.
Kueue admits these replacement pods through the normal pipeline, but the order of admission is not guaranteed -- any of the three Deployments could end up on the A100 node as the borrower.

For example, you might see `inference-fill-1` evicted instead of `inference-borrow` because after the reboot, `fill-1` happened to be the one borrowing from the A100 pool.
This is expected behavior.
The key takeaway is the same: `reclaimWithinCohort: Any` allows the lender to reclaim its GPU from *any* borrower, regardless of which Deployment holds it.
****

.reclaimWithinCohort Options
[sidebar]
****
The `reclaimWithinCohort` field has three possible values:

* `Never` (default) -- the lender cannot reclaim resources from borrowers
* `LowerPriority` -- the lender can reclaim only if the borrowing workload has a lower WorkloadPriorityClass than the pending workload
* `Any` -- the lender can reclaim from any borrowing workload regardless of priority

In this exercise you use `Any` for simplicity.
In production, `LowerPriority` is often preferred so that high-priority inference workloads borrowing GPU capacity are not evicted by low-priority training jobs.
****
