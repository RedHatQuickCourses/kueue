= Submit GPU Workloads
:navtitle: GPU Workloads

With Kueue fully configured, you now submit workloads to verify that admission, scheduling, and priority all work correctly.
All YAML files are in the `workloads/` directory.

== What You Will Test

You run three exercises that demonstrate different Kueue admission behaviors:

. *FIFO admission* -- three training Jobs with no priority, admitted in submission order
. *Priority-based admission* -- three training Jobs with different WorkloadPriorityClasses, admitted by priority value (not declaration order)
. *Queue isolation* -- an inference Deployment submitted to the T4 queue, proving that the LocalQueue -> ClusterQueue -> ResourceFlavor chain routes workloads to the correct GPU nodes

.Jobs vs Deployments in Kueue
[sidebar]
****
Kueue manages Jobs and Deployments differently:

* *Jobs* -- Kueue suspends the Job on creation (`spec.suspend: true`), queues it, and unsuspends it when admitted. The Job controller then creates pods. Jobs are finite -- they run to completion and release their resources.

* *Deployments* -- Kueue uses scheduling gates to hold pods until admission. Deployments are long-running -- they represent always-on services like model inference endpoints. Unlike Jobs, Deployments hold their GPU allocation indefinitely.

Both workload types go through the same LocalQueue -> ClusterQueue -> admission pipeline, but their lifecycle and resource release patterns are fundamentally different.
