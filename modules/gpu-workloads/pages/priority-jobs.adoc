= Training Jobs -- Priority-Based Admission
:navtitle: Priority Jobs

In this exercise, you submit three training Jobs with different WorkloadPriorityClasses.
The Jobs are deliberately declared in low, medium, high order in the YAML file to prove that Kueue admits by priority value, not by declaration order.

== Concepts

When workloads carry a `kueue.x-k8s.io/priority-class` label, Kueue uses the WorkloadPriorityClass value to determine admission order.
Higher values are admitted first, regardless of when they were submitted.

In this exercise, each Job requests 2 GPUs.
With 4 A100 GPUs available:

* `high-priority` (2 GPUs) + `medium-priority` (2 GPUs) = 4 GPUs -- fills all capacity
* `low-priority` (2 GPUs) must wait -- no capacity left

This demonstrates that Kueue uses priority, not FIFO, when WorkloadPriorityClasses are present.

== Lab: Submit Priority-Based Training Jobs

=== 1. Submit training jobs (priority-based admission)

a. Review `workloads/job-with-priority.yaml` before applying.
Only the first Job is shown here -- the other two (`training-job-medium-wpc`, `training-job-high-wpc`) follow the same structure with different priority classes:
+
[source,yaml]
----
apiVersion: batch/v1
kind: Job
metadata:
  name: training-job-low-wpc
  namespace: training-jobs
  labels:
    kueue.x-k8s.io/queue-name: training-queue
    kueue.x-k8s.io/priority-class: low-priority   <1>
spec:
  suspend: true
  template:
    metadata:
      annotations:
        run.ai/simulated-gpu-utilization: "40-60"
    spec:
      restartPolicy: Never
      containers:
      - name: training-workload
        image: registry.access.redhat.com/ubi9/ubi
        command: ["/bin/bash", "-c"]
        args:
        - |
          echo "=== Job: training-job-low-wpc (low-priority: 100) ==="
          ...
        resources:
          requests:
            cpu: "2"
            memory: "4Gi"
            nvidia.com/gpu: "2"                    <2>
          limits:
            nvidia.com/gpu: "2"
----
<1> The `priority-class` label references the WorkloadPriorityClass you created in xref:kueue-config:priority-classes.adoc#create-priority-classes[Create WorkloadPriorityClasses]. Each Job uses a different priority: `low-priority` (100), `medium-priority` (500), `high-priority` (1000). Kueue admits higher values first, regardless of declaration order in the YAML file.
<2> Each Job requests 2 GPUs (unlike the FIFO exercise which requested 1). With 4 A100 GPUs total, only 2 of the 3 Jobs can run simultaneously -- this forces contention so you can observe priority-based admission.
+
The Jobs are deliberately declared in low, medium, high order in the YAML to prove that Kueue reorders admission by priority value.

TIP: Even though `training-job-low-wpc` was declared first in the YAML, Kueue admitted `training-job-high-wpc` and `training-job-medium-wpc` first because they have higher WorkloadPriorityClass values.
*Priority trumps declaration order.*
This is one of Kueue's key advantages over basic Kubernetes scheduling -- it can reorder the admission queue based on business priority.

.How does the Low-Priority Job Get Admitted?
[sidebar]
****
After the `high-priority` or `medium-priority` job completes and releases 2 GPUs, Kueue automatically re-evaluates the pending queue.
The `low-priority` job is the only workload waiting, and 2 GPUs are now available, so Kueue admits it immediately.

This is *automatic* -- you do not need to resubmit or manually intervene.
Kueue continuously watches for capacity changes and admits pending workloads as resources free up.
****
