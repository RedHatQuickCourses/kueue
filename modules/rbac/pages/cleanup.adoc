=== 2. Clean up RBAC bindings

a. Remove admin bindings:
+
[source,console,subs="+quotes"]
----
$ **oc delete clusterrolebinding kueue-batch-admin-binding**
clusterrolebinding.rbac.authorization.k8s.io "kueue-batch-admin-binding" deleted

$ **oc delete rolebinding admin-edit -n training-jobs**
rolebinding.rbac.authorization.k8s.io "admin-edit" deleted
----
+
b. Remove user bindings:
+
[source,console,subs="+quotes"]
----
$ **oc delete rolebinding kueue-batch-user-binding -n training-jobs**
rolebinding.rbac.authorization.k8s.io "kueue-batch-user-binding" deleted

$ **oc delete rolebinding user1-edit -n training-jobs**
rolebinding.rbac.authorization.k8s.io "user1-edit" deleted
----

NOTE: The ClusterRoles themselves (`kueue-batch-admin-role`, `kueue-batch-user-role`) are managed by the Kueue operator -- do not delete them.

== Key Takeaways

.Three permission layers in Kueue on RHOAI
[sidebar]
****
When troubleshooting Kueue RBAC, remember that a user's effective permissions come from three independent layers:

*Layer 1: Kueue ClusterRoles* (`kueue-batch-admin-role`, `kueue-batch-user-role`) +
Created by the Kueue operator.
Controls access to Kueue resources (ClusterQueues, LocalQueues, Workloads) and workload types (Jobs, PyTorchJobs, RayJobs, etc.).
_You_ control who gets these permissions by creating bindings.

*Layer 2: RHOAI operator defaults* +
The RHOAI operator sets up cluster-wide permissions that make ResourceFlavors and WorkloadPriorityClasses accessible to all authenticated users.
These are _not_ part of the Kueue roles -- they exist regardless of your bindings.

*Layer 3: OpenShift built-in roles* (`edit`, `view`, `admin`) +
Kubernetes core resources (pods, logs, events, configmaps) are not covered by Kueue roles.
Without the `edit` role, users can submit Jobs and see Workloads, but cannot run `oc get pods` or `oc logs` to monitor their own work.

When something is unexpectedly allowed or denied, ask: _which layer_ is granting or blocking this?
****

.Binding type determines scope
[sidebar]
****
The _same_ ClusterRole behaves differently depending on the binding type:

* *ClusterRoleBinding* -- grants the role's permissions cluster-wide, including cluster-scoped resources (ClusterQueues, ResourceFlavors).
* *RoleBinding* -- grants only namespace-scoped permissions. Cluster-scoped resource permissions in the role are silently ignored.

This is why `admin` (bound via ClusterRoleBinding) can view ClusterQueues but `user1` (bound via RoleBinding) cannot -- even though they reference ClusterRoles with the same ClusterQueue permissions.
****
