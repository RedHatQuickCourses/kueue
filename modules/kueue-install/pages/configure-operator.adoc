= Configure the Kueue Operator
:navtitle: Configure Operator

This is the most critical configuration step in the entire course.
You patch the Kueue CR to disable LocalQueue defaulting and enable `BatchJob` integration.
Without these changes, Kueue silently routes workloads to the wrong queues and ignores Kubernetes Jobs entirely.

== Concepts

=== The Problem: LocalQueue Defaulting

When the Kueue operator starts on an RHOAI cluster, the platform auto-creates a set of default Kueue resources: a `default` ClusterQueue, `default-flavor` and `nvidia-gpu-flavor` ResourceFlavors, and a `default` LocalQueue in every Kueue-managed namespace.

Kueue has a feature called *LocalQueue defaulting* (enabled by default).
Any workload submitted *without* a `kueue.x-k8s.io/queue-name` label is automatically assigned to a LocalQueue named `default` in the same namespace.
The `default` LocalQueue routes to the `default` ClusterQueue, which uses generic ResourceFlavors with no nodeLabels, no tolerations, no preemption, and an inflated quota auto-detected from total cluster capacity.
This means:

* Workloads bypass your custom ResourceFlavors and land on any node -- not the intended GPU node
* No GPU pool isolation -- training and inference workloads share the same quota
* No preemption -- priority classes have no effect
* Quota limits are far too high -- a single queue with all cluster resources

WARNING: This defeats the entire purpose of configuring per-GPU-type queues, flavors, and quotas in this course.
If you skip this step, workloads will appear to work but will not use your custom Kueue configuration.

=== The Solution: QueueName Label Policy

You cannot delete the RHOAI-created defaults -- the RHOAI operator reconciles them back.
Instead, patch the Kueue CR to change `workloadManagement.labelPolicy` from `Default` to `QueueName`.

With `QueueName` policy, *only* workloads that carry an explicit `kueue.x-k8s.io/queue-name` label are managed by Kueue.
Unlabeled workloads are completely ignored -- they never enter the default LocalQueue, never reach the default ClusterQueue, and schedule normally via the Kubernetes scheduler.

[cols="1,1,3", options="header"]
|===
|Policy |Default? |Behavior

|`Default`
|Yes
|Kueue manages *all* workloads in managed namespaces. Workloads without a `kueue.x-k8s.io/queue-name` label are auto-assigned to a LocalQueue named `default` in the same namespace.

|`QueueName`
|No
|Kueue *only* manages workloads that carry an explicit `kueue.x-k8s.io/queue-name` label. Unlabeled workloads are completely ignored.
|===

=== The Problem: Missing BatchJob Integration

By default, the Red Hat build of Kueue does *not* include `BatchJob` (Kubernetes `Job`) in its managed frameworks.
Without it, any `Job` resources you create are ignored by Kueue -- they will not appear as workloads, will not be admitted, and will stay suspended forever.

Since `Job` is the natural fit for batch GPU training workloads, enabling `BatchJob` is essential for the exercises in xref:gpu-workloads:index.adoc[Submit GPU Workloads].

== Lab: Patch the Kueue CR

[[disable-defaulting]]
=== 1. Disable LocalQueue defaulting and enable BatchJob

a. Patch the Kueue CR:
+
[source,console,subs="+quotes"]
----
$ **oc patch kueues.kueue.openshift.io cluster --type merge -p '{**
  "spec": {
    "config": {
      "workloadManagement": {
        "labelPolicy": "QueueName"
      },
      "integrations": {
        "frameworks": ["BatchJob","Deployment","Pod","PyTorchJob","RayCluster","RayJob","StatefulSet","TrainJob"]
      }
    }
  }
}'
kueue.kueue.openshift.io/cluster patched
----

b. Verify the patch applied:
+
[source,console,subs="+quotes"]
----
$ **oc get kueues.kueue.openshift.io cluster -o jsonpath='{.spec.config}' | python3 -m json.tool**
{
    "integrations": {
        "frameworks": [
            "BatchJob",
            "Deployment",
            "Pod",
            "PyTorchJob",
            "RayCluster",
            "RayJob",
            "StatefulSet",
            "TrainJob"
        ]
    },
    "workloadManagement": {
        "labelPolicy": "QueueName"
    }
}
----
+
You should see `"labelPolicy": "QueueName"` under `workloadManagement` and `BatchJob` in the `frameworks` list.

IMPORTANT: With `QueueName` policy, unlabeled workloads bypass Kueue entirely -- no admission, no quota check, no workload object created.
They go straight to the Kubernetes scheduler as if Kueue did not exist.
If the workload has the right nodeSelector and toleration, it will land on a GPU node and consume a GPU outside of any quota.
This is by design -- it lets non-Kueue workloads (monitoring DaemonSets, test pods, etc.) run without disruption.
But it means *quota enforcement only applies to workloads that explicitly carry the queue-name label*.

NOTE: The RHOAI-created defaults (`default` ClusterQueue, `default-flavor`, `nvidia-gpu-flavor`, `default` LocalQueues) still exist after this patch -- but they are harmless.
No workload is auto-assigned to the `default` LocalQueue, so these resources sit idle.

.Production Recommendation
[sidebar]
****
In a production RHOAI cluster, you would apply the same approach: change the label policy to `QueueName` and build your own ResourceFlavors with nodeLabels targeting specific hardware, per-team ClusterQueues with appropriate quotas and preemption policies, and explicit LocalQueue assignments per namespace.

The `QueueName` policy gives you full control over which workloads Kueue manages.
This is especially important in mixed clusters where some namespaces run non-GPU workloads that should bypass Kueue entirely.
****
