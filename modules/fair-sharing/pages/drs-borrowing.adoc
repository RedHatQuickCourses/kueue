= Observe DRS Borrowing
:navtitle: DRS Borrowing

With Team B idle, Team A can use all 3 GPUs -- 2 from its own quota plus 1 borrowed from Team B's idle capacity.
In this section, you submit Team A's jobs and observe the DRS `weightedShare` values.

== References

* https://kueue.sigs.k8s.io/docs/concepts/cluster_queue/#fair-sharing[Kueue: Fair Sharing^]
* https://docs.redhat.com/en/documentation/openshift_container_platform/4.20/html-single/ai_workloads/index#configuring-fairsharing[Red Hat build of Kueue: Configuring Fair Sharing^]

== Lab: Submit Team A Jobs

=== 1. Submit Team A jobs (observe borrowing and DRS)

a. Review `workloads/job-fair-sharing-team-a.yaml` before applying.
The file contains 3 identical Jobs (`team-a-job-1` through `team-a-job-3`).
Here is one representative Job:
+
[source,yaml]
----
apiVersion: batch/v1
kind: Job
metadata:
  name: team-a-job-1
  namespace: training-jobs                             <1>
  labels:
    kueue.x-k8s.io/queue-name: team-a-queue            <2>
spec:
  suspend: true                                        <3>
  template:
    metadata:
      annotations:
        run.ai/simulated-gpu-utilization: "60-80"
    spec:
      containers:
      - name: training-workload
        image: registry.access.redhat.com/ubi9/ubi
        args:
        - |
          END=$((SECONDS+1800))                        <4>
          while [ $SECONDS -lt $END ]; do
            nvidia-smi; sleep 5
          done
        resources:
          requests:
            nvidia.com/gpu: "1"                        <5>
          limits:
            nvidia.com/gpu: "1"
----
<1> All 3 jobs are in the `training-jobs` namespace, routed through `team-a-queue`.
<2> The `queue-name` label routes these jobs to `team-a-cluster-queue` (weight 1, 2 GPU quota).
<3> `suspend: true` lets Kueue control admission. Jobs 1 and 2 are admitted using Team A's own quota. Job 3 exceeds the 2-GPU quota and borrows from Team B's idle capacity.
<4> Each job runs for 1800 seconds (30 minutes), giving you plenty of time to observe DRS values, check ClusterQueue status, and move to the next section to trigger preemption while the jobs are still running.
<5> Each job requests 1 GPU. With 3 jobs and only 2 GPUs in quota, the 3rd job must borrow -- this is what raises Team A's DRS.

d. Check the DRS observable -- this is unique to fair sharing:
+
[source,console,subs="+quotes"]
----
$ **oc get clusterqueue team-a-cluster-queue -o jsonpath='{.status.fairSharing}' | python3 -m json.tool**
{
    "weightedShare": 334
}
$ **oc get clusterqueue team-b-cluster-queue -o jsonpath='{.status.fairSharing}' | python3 -m json.tool**
{
    "weightedShare": 0
}
----
+
Team A's `weightedShare` should be *non-zero* -- it is using 3 GPUs against a nominal quota of 2, meaning it is borrowing.
Team B's `weightedShare` should be *0* -- no usage at all.

.Why 334 and not 1000?
[sidebar]
****
In xref:index.adoc[the introduction], the DRS formula was presented as `(borrowing / lendable) x 1000 / weight`, which gives 1000 for this scenario.
That is a simplified version to build intuition.

The actual formula Kueue uses to compute `weightedShare` is:

`weightedShare = 1000 x (usage - nominal) / (cohort_total x weight)`

For Team A: `1000 x (3 - 2) / (3 x 1) = 334`

The difference is that the real formula divides by the *total cohort capacity* (3 GPUs), not just the lendable portion (1 GPU).
This produces a value between 0 and 1000 that represents how much of the *entire cohort* the queue is over-consuming, normalized by weight.

* `weightedShare = 0` means the queue is at or below its nominal quota -- safe from preemption
* `weightedShare > 0` means the queue is borrowing -- the higher the value, the more over-entitled it is, and the first to be preempted

The exact number does not matter to students.
What matters is the *relative comparison*: Team A = 334 vs Team B = 0.
Kueue always preempts the queue with the highest `weightedShare`.
****
